# 13. Sequence-діаграми за Gherkin-сценаріями (S1–S6) та активація всіх учасників

* Статус: прийнято
* Дата: 2026-10-23
* Контекст: Завдання 3 (`task-3/`), `task-3/sequence.md`, `task-3/sequence.puml`
* Замінює: `docs/adr/0012-sequence-per-scenario.md` у частині кількості діаграм і правил activation bars

## Context and Problem Statement
ADR 0012 описував дві діаграми (US-01 і US-02), activation bars лише для частини учасників і виняток для `Database` у US-01. Відгук викладача вимагає окрему діаграму на кожен сценарій, `activate`/`deactivate` для всіх сервісів і БД, а також явну перевірку `USER.role` через `Database`. Потрібно визначити набір сценаріїв і правила для діаграм.

## Decision Drivers
* Одна діаграма — один Gherkin-сценарій з `task-2/README.md`, розд. 3.
* Кожна діаграма має щонайменше один комбінований фрагмент.
* Activation bars у всіх учасників, які беруть участь у діаграмі, включно з `Database`.
* `USER.role` читається тільки через `Database` (`getSession`, `getUserRole`).
* Завдання 2 не змінюється.

## Considered Options
* **Варіант 1:** дві діаграми (ADR 0012).
* **Варіант 2:** чотири діаграми за сценаріями: S1 успіх, S2 нестача, S3 відмова оплати, S4 без оплати (обрано).
* **Варіант 3:** додати в Завдання 2 новий Gherkin «нестача при оформленні» і зробити діаграму на нього.

## Decision Outcome
Обрано **варіант 2** з доповненням **варіанта 3**: шість діаграм S1–S6.
* S1: US-01 «Створення замовлення з Price Snapshot і резервуванням залишку». Фрагменти: `alt` (EARS-14, EARS-03), `critical`, `loop`.
* S2: US-02 «Повторна оплата відхиляється, якщо товару немає на складі». Фрагмент: `break`.
* S3: US-02 «Відмова платежу скасовує резерв». Фрагменти: `critical`, `loop`.
* S4: US-02 «Оплата не обрана (extend не виконується)». Фрагмент: `opt`.
* S5: US-02 «Успішна онлайн-оплата». Фрагменти: `opt` з `alt` (approved → `Paid`; declined → як S3), `critical`, `loop`.
* S6: US-01 «Оформлення з нестачею залишку». Фрагмент: `break`. Gherkin додано в `task-2/README.md`, розд. 3 (варіант 3). Завдання 2 змінено лише доповненням сценарію.

Правила:
* Кожен учасник, що бере участь у діаграмі, має `->>+` / `-->>-` на кожен виклик.
* Роль перевіряється через `UserService` → `Database.getSession` → `Database.getUserRole`.
* Учасники з ADR 0011 збережені. `PaymentGateway` є в S3, S4 і S5.
* Mermaid веде activation bars лінійно: активація, відкрита до `alt`, закривається один раз (після фрагмента або в одній гілці). Пунктирні повернення в гілках без деактивації.

### Consequences
* Good: кожна діаграма трасується до одного Gherkin-сценарію.
* Good: activation bars показують роботу кожного учасника, включно з `Database`.
* Good: перевірка ролі через БД відповідає зауваженню викладача.
* Good: нестача залишку покрита двома сценаріями: при оформленні (S1, S6) і при повторній оплаті (S2).
* Bad: шість діаграм замість двох, більше файлів для пояснення.
* Bad: відхилення від прикладу з ADR 0013 (`UserService-->>-WebApp: 401` всередині `alt`) через лінійні activation bars Mermaid; повернення в гілках пунктирні.

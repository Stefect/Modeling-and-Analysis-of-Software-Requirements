# 6. Абстрактний актор `User` як генералізація для `Customer` та `Seller`

* Статус: прийнято
* Дата: 2026-10-13
* Контекст: Завдання 2 (`task-2/`)

## Context and Problem Statement
`Customer` і `Seller` є різними ролями, але обидві використовують автентифікацію та управління профілем. У першій ітерації вони були незалежними акторами, що призводило до дублювання опису автентифікації.

## Decision Drivers
* Єдина точка автентифікації.
* Чіткі рольові права (RBAC).
* Відповідність ERD, де `USER` — базова таблиця з полем `role`.

## Considered Options
* **Варіант 1:** Два незалежних актори `Customer` і `Seller`.
* **Варіант 2:** Один актор `User` з рольовим розділенням всередині системи.
* **Варіант 3:** Абстрактний актор `User` з успадкуванням `Customer` і `Seller`.

## Decision Outcome
Обрано **Варіант 3**. `User` — абстрактний базовий актор, `UC_Auth` прив'язаний до нього.

### Consequences
* Good: єдина точка входу для автентифікації (`UC_Auth`).
* Good: рольові дозволи описуються на рівні спадкових акторів.
* Good: відповідає ERD: `USER` — базова таблиця, `role` визначає роль.
* Bad: потрібно явно описувати, які UC належать лише окремій ролі, щоб не успадкувати зайві права.

## Pros and Cons of the Options

### Варіант 1: Два незалежних актори
* Good: простота опису кожної ролі окремо.
* Bad: дублювання автентифікації, порушення DRY.

### Варіант 2: Один актор без розділення
* Good: мінімум акторів.
* Bad: втрачається семантика ролей, складніші дозволи.

### Варіант 3: Абстрактний `User` з успадкуванням (обрано)
* Good: одна автентифікація, чіткі ролі, відповідність ERD.
* Bad: потреба в явному визначенні прав окремих ролей.

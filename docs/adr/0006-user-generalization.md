# 6. Абстрактний актор `User` як генералізація для `Customer` та `Seller`

* Статус: прийнято
* Дата: 2026-10-13
* Контекст: Завдання 2 (`task-2/`)

## Контекст та постановка проблеми
`Customer` і `Seller` є різними ролями, але обидві використовують автентифікацію та управління профілем. У першій ітерації вони були незалежними акторами, що призводило до дублювання опису автентифікації.

## Розглянуті варіанти
* **Варіант 1:** Два незалежних актори `Customer` і `Seller`. Дублювання автентифікації, порушення принципу DRY.
* **Варіант 2:** Один актор `User` з рольовим розділенням всередині системи. Втрачається семантика ролей у діаграмі.
* **Варіант 3:** Абстрактний актор `User` з успадкуванням `Customer` і `Seller`.

## Рішення
Обрано **Варіант 3**. `User` — абстрактний базовий актор, `UC_Auth` прив'язаний до нього.

### Позитивні наслідки
* Єдина точка входу для автентифікації (`UC_Auth`).
* Рольові дозволи (RBAC) описуються на рівні спадкових акторів.
* Відповідає ERD: `USER` — базова таблиця, `role` визначає роль.

### Негативні наслідки
* Потрібно явно описувати, які UC належать лише окремій ролі, щоб уникнути успадкування зайвих прав.

# ADR-0015: Вибір Activity-діаграми зі swimlanes для моделювання бізнес-процесу

* **Статус:** прийнято
* **Дата:** 2026-10-27

## Контекст
У Завданні 4 вимагається описати один бізнес-процес «Оформлення та оплата замовлення» однією точною формальною формою без використання двох нотацій одночасно. Потрібно відобразити початок/кінець, дії, потоки керування, розгалуження, паралельні гілки (`fork/join`) та ролі (`swimlanes`).

## Decision Drivers (Фактори прийняття рішення)
* **Наочність розподілу відповідальності:** Потрібно чітко розмежувати зони відповідальності між 4 акторами (`Customer`, `WebApp`, `OrderService`, `PaymentGateway`).
* **Візуалізація атомарності:** Необхідно наочно показати межі ACID-транзакції та паралельне виконання дій в БД (`ORDER.status = Paid` та `insertOutbox`).
* **Сумісність із Mermaid та GitHub:** Нотація має підтримуватися інструментами автоматичного рендерингу Markdown у GitHub без додаткових сторонніх плагінів чи графічних серверів.

## Розглянуті варіанти

### Варіант 1: Машина станів (`stateDiagram-v2`)
* **Плюси:** Має нативні нотації для `<<fork>>` та `<<join>>`; чітко описує стани сутності `ORDER` (`Pending`, `Paid`, `Unpaid`, `Cancelled`).
* **Мінуси:** Не має підтримки доріжок ролей (`swimlanes`), що унеможливлює наочний розподіл відповідальності між Покупцем, Фронтендом, Бекендом та Платіжним шлюзом.

### Варіант 2: Activity-діаграма по доріжках на базі `flowchart TB` (п'ять інлайн-блоків у порядку процесу)
* **Плюси:** Блоки йдуть у порядку виконання процесу; кожен блок описує один етап (оформлення, сесія, створення, списання, фіксація оплати), що зменшує перетини ліній; переходи між доріжками позначені вузлами `→ X` / `← X`; паралельні гілки `fork/join` видно в доріжці `OrderService`; нативно рендериться прямо в GitHub Markdown.
* **Мінуси:** У Mermaid `flowchart` відсутні нативні UML-нотації fork/join bars, тому використовуються умовні круглі вузли `(( fork ))` та `(( join ))`. Цілісність графа між блоками перевіряється скриптом, а не рендером.

### Варіант 3: Activity-діаграма у PlantUML
* **Плюси:** Підтримує повноцінний нативний синтаксис UML Activity Diagrams (включно з класичними fork/join лініями та swimlanes `|Customer|`).
* **Мінуси:** Потребує зовнішнього PlantUML-сервера або додаткових складних розширень для рендерингу у Markdown, що ускладнює перегляд діаграми безпосередньо у репозиторії GitHub.

## Рішення
Обрати **Варіант 2 (Activity-діаграма по доріжках на базі `flowchart TB`, розбита на п'ять інлайн-блоків у порядку процесу)**.

### Наслідки
* **Позитивні:** Розмежування відповідальності між доріжками збережено; опис атомарної транзакції оплати залишився прозорим; кожен блок читабельний окремо і автоматично рендериться в GitHub.
* **Негативні:** Оскільки використовується `flowchart`, вузли `fork` та `join` позначено умовно круглими вузлами замість класичних UML-ліній. Цілісність переходів між блоками перевіряється скриптом (`→` / `←`), а не візуально.

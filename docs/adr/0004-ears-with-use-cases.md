# 4. Комбінація EARS-вимог, Use Case діаграми та Gherkin для опису функціональності

* Статус: прийнято
* Дата: 2026-10-13
* Контекст: Завдання 2 (`task-2/`)

## Context and Problem Statement
Потрібно описати функціональні вимоги маркетплейсу так, щоб їх можна було однозначно перевірити та трасувати до сутностей ERD (Завдання 1). Текстові user stories без формалізації допускають різні трактування, а лише діаграма не описує умови та реакцію системи.

## Decision Drivers
* Однозначність і перевірюваність кожної вимоги.
* Видимість взаємодії акторів і залежностей між прецедентами (`<<include>>`, `<<extend>>`).
* Трасування вимог до сутностей ERD і до прецедентів.

## Considered Options
* **Варіант 1:** Тільки User Stories з Gherkin-сценаріями.
* **Варіант 2:** Тільки EARS-вимоги без діаграми.
* **Варіант 3:** EARS-вимоги + Use Case діаграма + User Stories з Gherkin.

## Decision Outcome
Обрано **Варіант 3**. EARS задає формальні умови кожної вимоги, Use Case діаграма показує акторів, прецеденти та їх залежності, Gherkin перетворює вимоги на перевірювані сценарії.

### Consequences
* Good: кожна вимога має тип EARS (Ubiquitous, Event-driven, State-driven, Optional, Unwanted behavior), що зменшує двозначність.
* Good: явне розмежування `<<include>>` та `<<extend>>` у діаграмі.
* Good: наскрізне трасування через `task-2/trace-matrix.md`.
* Bad: більший обсяг документації, ніж при використанні лише user stories.
* Bad: потрібна синхронізація трьох форм опису (EARS, діаграма, Gherkin) при змінах.

## Pros and Cons of the Options

### Варіант 1: Тільки User Stories з Gherkin
* Good: простота і швидкість написання.
* Bad: недостатня точність, ризик двозначності формулювань.

### Варіант 2: Тільки EARS без діаграми
* Good: формальні умови кожної вимоги.
* Bad: не видно структуру взаємодій і залежності `include`/`extend`.

### Варіант 3: EARS + Use Case діаграма + Gherkin (обрано)
* Good: точність, видимість взаємодій, перевірюваність.
* Bad: більший обсяг і потреба синхронізації.

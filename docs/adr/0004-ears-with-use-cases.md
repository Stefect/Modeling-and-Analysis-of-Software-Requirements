# 4. Комбінація EARS-вимог та Use Case діаграми для опису функціональності

* Статус: прийнято
* Дата: 2026-10-13
* Контекст: Завдання 2 (`task-2/`)

## Контекст та постановка проблеми
Потрібно описати функціональні вимоги маркетплейсу так, щоб їх можна було однозначно перевірити та трасувати до сутностей ERD (Завдання 1). Текстові user stories без формалізації допускають різні трактування, а лише діаграма не описує умови та реакцію системи.

## Розглянуті варіанти
* **Варіант 1:** Тільки User Stories з Gherkin-сценаріями. Недостатня точність, ризик двозначності формулювань.
* **Варіант 2:** Тільки EARS-вимоги без діаграми. Втрачається структура взаємодій акторів, неможливо показати залежності `include`/`extend`.
* **Варіант 3:** EARS-вимоги + Use Case діаграма + User Stories з Gherkin.

## Рішення
Обрано **Варіант 3**. EARS задає формальні умови кожної вимоги, Use Case діаграма показує акторів, прецеденти та їх залежності, Gherkin перетворює вимоги на перевірювані сценарії.

### Позитивні наслідки
* Кожна вимога має єдиний тип EARS (Ubiquitous, Event-driven, State-driven, Optional, Unwanted behavior), що зменшує двозначність.
* Явне розмежування `<<include>>` та `<<extend>>` у діаграмі.
* Наскрізне трасування через `trace-matrix.md`.

### Негативні наслідки
* Більший обсяг документації, ніж при використанні лише user stories.
* Потрібна синхронізація трьох форм опису (EARS, діаграма, Gherkin) при змінах.

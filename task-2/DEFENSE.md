# DEFENSE — Завдання 2: Вимоги та Use Cases

# 1. Намір і критерії

*Намір* — розробити повний пакет функціональних вимог (EARS), User Stories із Gherkin-сценаріями та Use Case діаграму для мультивендорного маркетплейсу, забезпечивши 100% узгодженість із концептуальною моделлю даних (ERD) із Завдання 1.

*Критерії готовності:*
> Усі функціональні вимоги записані за строгим синтаксисом EARS.
> Use Case діаграма містить акторів (із генералізацією `User`), прецеденти використання та зв'язки `<<include>>` / `<<extend>>`.
> Всі Use Cases прив'язані до відповідних сутностей ER-моделі (`USER`, `STORE`, `PRODUCT`, `ORDER`, `ORDER_ITEM`, `REVIEW`).
> Створено матрицю трасування (Traceability Matrix) та визначено межі системи (Out of Scope).

# 2. Топ-3 розбіжності, які знайшов і виправив у ході розробки

*1. Некоректний зв'язок між замовленням та оплатою на Use Case діаграмі*
- **Розбіжність:** Початкова генерація AI показувала оплату як обов'язковий `<<include>>` для створення замовлення.
- **Виправлення:** Зв'язок змінено на `<<extend>>`, оскільки оплата може відбуватися пізніше або готівкою при отриманні, а обов'язковим `<<include>>` зроблено сценарій фіксації ціни `unit_price`.
- **Чому:** Оплата є опціональним розширенням процесу створення замовлення, а не його невід'ємною частиною в момент створення.

*2. Відсутність абстрактного актора та генералізації*
- **Розбіжність:** Актори `Customer` та `Seller` були автономними без спільного рольового батька.
- **Виправлення:** Додано абстрактного актора `User` та зв'язки успадкування `Customer --|> User` і `Seller --|> User`.
- **Чому:** Обидві ролі вимагають базової автентифікації та профілю користувача в системі.

*3. Нечіткі вимоги без прив'язки до моделі даних*
- **Розбіжність:** Первинні вимоги EARS описували поведінку у вільному стилі без згадки атрибутів та сутностей бази даних.
- **Виправлення:** Вимоги переписано із чітким зазначенням сутностей (`ORDER`, `ORDER_ITEM`, `stock_quantity`, `unit_price`).
- **Чому:** Це забезпечує наскрізне трасування від вимог до фізичної бази даних.

# 3. Ключове рішення (ADR / Architecture)

*Вибір синтаксису EARS та зв'язків Use Case*
- **Рішення:** Обрано комбінацію паттернів EARS (Ubiquitous, Event-driven, State-driven, Optional, Unwanted Behavior) та сувору деталізацію Use Cases.
- **Обґрунтування:** Це дозволяє повністю усунути двозначність вимог перед передачею проєкту в розробку та гарантує цілісність даних (зокрема Price Snapshot у `ORDER_ITEM`).

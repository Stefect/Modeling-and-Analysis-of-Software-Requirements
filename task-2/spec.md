# Специфікація вимог: Маркетплейс (Завдання 2)

## 1. Намір (Intent)
Формалізувати та структурувати функціональні вимоги до мультивендорного маркетплейсу, побудувати сценарії використання (Use Cases) та забезпечити повну трасованість вимог до сутностей даних із Завдання 1 (`USER`, `STORE`, `PRODUCT`, `ORDER`, `ORDER_ITEM`, `REVIEW`)[cite: 18].

## 2. Актори (Actors)
- **Людина (Human Actors):**
  - `User` (Абстрактний користувач системи — базовий рольовий предок).
  - `Customer` (Покупець, успадковує `User`): шукає товари, додає їх у кошик, оформлює замовлення (`ORDER`), залишає відгуки (`REVIEW`)[cite: 18].
  - `Seller` (Продавець, успадковує `User`): володіє магазинами (`STORE`), керує каталогом товарів (`PRODUCT`)[cite: 18].
- **Зовнішня система (External System):**
  - `Payment Gateway` (Платіжний шлюз): обробляє онлайн-транзакції та повертає статус оплати.

## 3. Критерії прийняття (Acceptance Criteria)
1. **Формат EARS:** Усі вимоги сформульовані за строгим синтаксисом EARS (Ubiquitous, Event-driven, State-driven, Optional, Unwanted behavior).
2. **Невід'ємні зв'язки з ERD:** Усі Use Cases прив'язані до сутностей бази даних (`USER`, `STORE`, `PRODUCT`, `ORDER`, `ORDER_ITEM`, `REVIEW`)[cite: 18].
3. **Модель Use Cases:** Наявна генералізація акторів (`Customer`/`Seller` $\rightarrow$ `User`), зв'язки `<<include>>` (обов'язковий Price Snapshot у `ORDER_ITEM`) та `<<extend>>` (опціональна оплата)[cite: 17].
4. **Матриця трасування:** Наявні зв'язки $N:M$ між EARS та Use Cases, а також щонайменше 1 вимога винесена в Out of Scope з обґрунтуванням[cite: 21].
5. **Рендеринг діаграми:** Mermaid-діаграма рендериться на GitHub без помилок у компактній вертикальній орієнтації.
